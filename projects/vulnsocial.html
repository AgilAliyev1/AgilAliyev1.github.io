A web application assessment of a containerised social network built for training: 14 confirmed findings, chained from a message in an inbox to root on the host.

0x01 · objective

Objective

Find and exploit weaknesses in the application and its supporting services, show their real impact by chaining them, and give remediation advice for each one.

Scope: two VirtualBox machines provisioned for the exercise. No production data and no third-party systems.
0x02 · technologies

Target & tools

  • Node.js / Express
  • EJS
  • MongoDB
  • PostgreSQL
  • Docker
  • nginx
  • Nmap
  • Gobuster
  • curl
  • Netcat
  • psql
0x03 · method

Method

Black-box to grey-box, aligned with PTES and the OWASP Testing Guide. I began without credentials and later used registered test accounts.

  1. Reconnaissance: host discovery, port and service scanning, content discovery.
  2. Enumeration: technology stack, endpoints, accounts and roles.
  3. Vulnerability analysis of authentication, sessions, input, files and database access.
  4. Exploitation, to move each candidate from suspected to confirmed.
  5. Post-exploitation, chaining findings towards the host.
  6. Reporting, with evidence and a prioritised remediation roadmap.
0x04 · findings

Findings

3 critical, 7 high, 4 medium. The ones that mattered most:

  1. Docker socket exposed inside the application container critical
    Code running in the container could control Docker on the host, and through it the host itself.
  2. Stored XSS leading to admin session hijacking critical
    Message content was not sanitised, and an automated admin bot opened every message.
  3. Arbitrary file write critical
    A view template could be overwritten, leaving a persistent backdoor.
  4. Server-side template injection high
    Admin post content was evaluated as a template, giving command execution as root in the container.
  5. PostgreSQL command execution high
    An over-privileged database role could run operating system commands.
  6. Path traversal, unrestricted upload, weak session settings and hard-coded secrets high
    Each one was confirmed separately.
Template injection was rated high, not critical, because re-testing showed it needed an admin session.
0x05 · chain

Attack chain

  1. Send a stored XSS payload to the admin from a registered account.
  2. The admin bot opens it and its session cookie is captured.
  3. Use the admin session to trigger template injection: root in the container.
  4. Recover configuration and map the internal Docker network.
  5. Use the exposed Docker socket to reach the host file system: root on the host.
0x06 · fixes

Remediation priorities

  1. Remove the Docker socket from the application container.
  2. Sanitise and encode user content, and never render it as a template.
  3. Restrict uploads by content type and size, stored outside the web root.
  4. Move secrets to a secrets manager and rotate all of them.
  5. Harden session cookies, file paths and database privileges.

The full report is 39 pages. Passwords, secrets and session cookies are redacted.
